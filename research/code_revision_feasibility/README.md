# Timestamped source-revision feasibility

CodeBench execution records contain a CODE section attached to each TEST/SUBMITION timestamp. All 153,931 SUBMITION records in the audited 2016-1 archive contain exactly one nonempty CODE section. We recover those records directly by archive path and file-event index; final saved `.py` files and reconstructed editor buffers are not substituted for historical snapshots. Submitted programs are never executed.

Across all original partitions, the earlier two-or-more-submission future-target rule yields 11,499 structurally eligible pairs. Of these, 11,492 use the same source path at both endpoints, 10,440 have different endpoint text, 8,769 have AST-parseable endpoints, and 7,872 have a numeric target and known training item. With at least three submissions, the corresponding counts are 8,070 structural pairs from 446 users, 8,064 same-path pairs, 7,728 changed endpoints, 5,992 parseable endpoint pairs, and 5,346 numeric/train-supported targets. These counts use literal positional endpoints; a preliminary null-skipping groupby aggregation was corrected before reporting or modeling. The independent loop and positional two-snapshot counts agree exactly.

Bounded verification of four actual raw source logs confirms processed record/code hashes, ordered source/target timestamps, and snapshot linkage. The deliberately selected examples include text change, invalid-to-valid syntax, identical endpoints, and a three-snapshot episode that changes and then returns to the original text. The last example demonstrates that strictly intermediate text can contain variation absent from endpoint text. These examples are feasibility checks, not population rates. Token and AST normalization were checked for those examples only; a full-population semantic-change rate is not claimed.

Recorded source revisions are therefore usable for a prespecified observational information-feature experiment. They are not labeled semantic repairs or learning events. In fact, 2,416 adjacent pairs have identical code hashes but different known grades. Unknown grading context, nondeterminism, inputs, or logging behavior can matter; code equality does not establish outcome equality. Source times have one-second precision, feedback-delivery timing is not independently established, and the original data contain one within-file backward clock transition. Some submission-contiguous episodes contain TEST activity on other exercises. Original assessment metadata provide exercise IDs and windows, but no complete verified problem statements or knowledge-component graph.

A defensible experiment must compare identical eligible pairs at H1: nuisance/history/feedback/time/count controls; then first/final code representations; then strictly intermediate code. Endpoint differences are deterministic functions of endpoints and are not new process information. All 2016-1 evaluation splits were already consumed, so fresh held-out users from 2016-2 are used in the separate `research/revision_information/` experiment.

`coverage.json`, `selected_examples.json`, and `raw_verification.json` contain archive paths/user identifiers and are local audit material, not safe public aggregate exports. `coverage.csv` and `three_snapshot_coverage.json` contain aggregate counts. Scripts reproduce checks from locally acquired official archives.
